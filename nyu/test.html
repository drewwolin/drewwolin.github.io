📐 ER Diagram Basics: Shapes & Symbols
ENTITY
Strong Entity: An independent object (e.g., Student). Becomes a table.
WEAK
Weak Entity: Depends on an owner (e.g., OrderLine). Requires Composite PK.
Name
Attribute: A property of an entity. Becomes a table column.
ID
Primary Key (PK): Unique identifier. Underlined in diagrams.
Verb
Relationship: Association between entities. Diamonds in Chen notation.
🔗
Foreign Key (FK): Attribute referencing a PK in another table. Links entities.
Notation icons represent Conceptual models, while FKs/Tables represent the Physical database.
📊 ER Diagram Basics
Entity An abstract object (person, place, thing, event) represented as a rectangle. Becomes a table.
Attribute A property describing an entity, shown as an oval. Becomes a column. Has a domain (data type).
Primary Key (PK) Attribute(s) uniquely identifying each instance. Underlined in diagrams. Should be stable.
Relationship An association between entities, shown as a diamond on a connecting line. Named with a verb.
Foreign Key (FK) An attribute referencing another table's primary key. Implements relationships in the relational model.
🦶 Crow's Foot Notation
Symbol Min Max Meaning
1 1 Exactly one (mandatory)
1 N One or more (mandatory many)
0 1 Zero or one (optional)
0 N Zero or more (optional many)
Notation goes on the opposite side of the relationship. The symbol next to Entity B describes how many B's each A can have.
🔗 Relationship Cardinalities
One-to-One (1:1)
A ──||────||── B
Student ↔ University Email
Each A has max 1 B; each B has max 1 A
One-to-Many (1:N)
A ──||────○<── B
Department → Professors
Each A has many B's; each B has max 1 A
Many-to-Many (M:N)
A ──>○────○<── B
Students ↔ Courses
Each A has many B's; each B has many A's
⚠️ Why Databases? (Data Anomalies)

Insertion

Can't add new data without unrelated "filler" data

Deletion

Deleting one fact accidentally removes unrelated data

Update

Same fact stored multiple times → inconsistency risk

Solution: Normalize data into separate tables with foreign keys. Each fact stored once.
🔄 ER Diagram → Relational Schema
0
Verify: All entities have PKs; all relationships have min/max cardinalities on both sides
1
Entities → Tables: Each entity becomes a table; attributes become columns
2
M:N → Bridge Table: Create new table with FKs to both entities (+ relationship attributes)
3
1:N → Foreign Key: Add FK to the "many" side table pointing to the "one" side
4
1:1 → FK or Merge: Add FK to either table, or merge tables if appropriate
💾 SQL: CREATE TABLE
CREATE TABLE Customer (
  id INT,
  name VARCHAR(100),
  email VARCHAR(255),
  created_at DATE,
  PRIMARY KEY(id)
);
Adding Foreign Keys
CREATE TABLE Order (
  id INT,
  customer_id INT NOT NULL,  -- mandatory
  amount FLOAT,
  PRIMARY KEY(id),
  FOREIGN KEY (customer_id) 
    REFERENCES Customer(id)
);
🔒 SQL: Enforcing Cardinality
NOT NULL Enforces mandatory participation (min = 1). The FK cannot be empty.
UNIQUE Enforces max = 1. Combined with FK, creates 1:1 relationship.
Example: Enforcing 1:1
CREATE TABLE Rate (
  id INT,
  customer_id INT NOT NULL,
  price FLOAT,
  PRIMARY KEY(id),
  UNIQUE (customer_id),
  FOREIGN KEY (customer_id) 
    REFERENCES Customer(id)
);
📝 Common SQL Data Types
Type Use For Example Type Use For Example
INT Whole numbers, IDs 42, 1000 DATE Dates only '2024-01-15'
FLOAT / DECIMAL Decimals, prices 19.99, 3.14 DATETIME Date + time '2024-01-15 14:30:00'
VARCHAR(n) Variable-length text 'Hello' (max n chars) BOOLEAN True/false flags TRUE, FALSE
TEXT Long text, descriptions Full paragraphs ENUM(...) Fixed set of values ENUM('S','M','L','XL')
Use DECIMAL(10,2) for money (exact precision). Use VARCHAR with appropriate limits rather than TEXT when possible.
